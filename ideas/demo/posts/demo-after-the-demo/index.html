看完一个漂亮的 Agent 演示，我更想问什么

让人惊艳的那十秒之外，还有一整天真正要完成的工作。这个落差，可能比演示本身更值得聊。

#Agents#Infra
这一页先把“做到了”和“我能用”分开我会先做一个很小的实验也许机会就在那些“不够酷”的地方

演示结束时，我经常有两种冲动：先说一句“这也行？”，然后想看看没剪进去的那几次。

不是为了泼冷水。只是如果真要把自己的工作交出去，我想知道的事情，和一段视频能证明的事情，可能不完全一样。

先把“做到了”和“我能用”分开

假设一个 Agent 能替我完成一次资料整理。那很好。但下一次换了网站、碰到缺失字段，或者资料互相矛盾，它会怎样？我更想看到这些不那么顺利的时刻。

“这次成功了”是个好起点，但我真正想问的是：什么时候它知道自己还没成功？

演示文字 · 一个待验证的问题

这不是一个对所有产品都适用的结论。对低成本的试验，我愿意让它多试；对会直接影响后续决策的任务，我需要看见证据和边界。

我会先做一个很小的实验

先不急着评价整个系统。挑一个具体任务，把失败样本留下来，再观察它能不能识别失败，以及用户需要补多少工作。

python
# 虚构的小样本，只示意“结果”和“识别失败”是两回事。
runs = [
    {"completed": True,  "asked_for_help": False},
    {"completed": False, "asked_for_help": True},
    {"completed": False, "asked_for_help": False},
]

silent_failures = sum(
    not run["completed"] and not run["asked_for_help"]
    for run in runs
)
print(silent_failures)  # 1
还没想清楚

过于频繁地求助也会让人烦。这条边界可能需要按任务成本来定，而不是给所有任务一个统一阈值。

也许机会就在那些“不够酷”的地方

我现在更想继续看的，是记录、评估、恢复，以及人如何顺利接手。不是因为这些已经被证明是答案，而是它们更接近“明天我愿不愿意继续用”的问题。

  • 失败能不能复现，而不只是重跑直到成功？
  • 用户能不能知道它现在卡在哪里？
  • 换个人接手时，能不能保留已有的上下文？

这类问题值得沿着工程团队的公开记录继续往下追，不必只停在产品演示里。[1]

先把这个念头放在这里。下一次看到漂亮的 demo，还是会心动。但我想多留十分钟，看看它不漂亮的那一面。

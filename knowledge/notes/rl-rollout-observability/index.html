多轮 RL：从指标监控到 Rollout 轨迹检查

Rollout 既是策略行为也是后续学习的数据；训练期间需把完整轨迹、评分与环境错误关联起来，检查模型正在学会什么。

TAKE THIS WITH YOU · 记忆点

指标告诉你结果如何，轨迹帮助你理解结果怎么来的。

Rollout 既是行为，也是下一轮学习的数据；训练中检查轨迹就是检查正在强化什么。

01

理解概念

回到当时的问题

看 MiMo RL 直播时，注意到团队在训练期间从 rollout 日志发现 bad patterns，并决定在后续 Pro run 中移除 cyber 数据集。由此反思：训练启动后不能只看聚合指标，也需要检查交互过程。

为什么轨迹检查是训练闭环的一部分

在线 RL 的闭环是：当前策略产生轨迹，评价器打分，训练系统更新策略，新策略继续产生轨迹。Rollout 同时反映当前行为，并成为接下来学习的数据。若不良行为得到正反馈，它就可能被后续优化强化。

成功率、平均奖励等聚合指标说明结果趋势；轨迹展示模型如何观察、行动、使用工具和处理反馈。把评分记录关联到轨迹，才能进一步诊断哪些行为得到了奖励。

如何把检查落到训练流程

保留任务标识、数据来源、策略版本、逐轮动作与反馈、终止原因、奖励和环境错误，使完整交互可以回放。定期随机抽查，同时针对高奖励但行为异常、失败、轮数或工具调用量激增的样本做专项检查。

随机抽样与异常触发检查互补：坏模式可能出现于指标看起来正常的时候。诊断时分清策略失败、环境或网络故障、评价器错误；不要把基础设施故障直接解释为模型能力不足。

检查结果可以影响任务筛选、奖励修订和训练是否继续，但具体干预要基于复核。单条异常轨迹不能自动证明某个数据源整体有问题。

长交互与规模扩大后的耦合

十轮交互已经可能出现重复尝试、忽略反馈等行为。更长的任务会扩大早期决策的后续影响，增加最终成败归因的难度；难度还取决于奖励稀疏程度和错误能否恢复，不能只数轮数。

多任务、多 harness 与分布式采样使行为诊断更复杂：数据来源、交互协议、任务耗时和训练配比会共同影响进入更新的数据。基本闭环仍可与业务 RL 对照，但规模扩大带来相互耦合的工程问题。

训练成功率也会随任务筛选和配比改变，因此应结合条件可比的独立评测观察泛化，不能把训练指标的上升全部归因为能力提升。

MiMo 公告的证据边界

本次讨论依据用户提供的直播截图：团队报告了训练集群与 grader 的网络连接问题，并另行说明从 rollout 日志发现不良模式，决定移除后续 Pro run 的 cyber 数据。公告没有证明这两件事具有因果关系。

截图能证明训练期间存在日志检查及据此干预；不能证明有人逐条实时盯守，也不能证明使用了专门的实时轨迹看板。定期抽查、异常告警后排查或其他方式都可能产生这一通知。

公告没有披露 bad patterns 的具体内容，不能直接断言是 reward hacking。官方发布页展示的是已有模型继续进行 RL 的阶段，不能用这段直播还原模型从预训练到可用产品的完整形成过程。

02

把概念放进示例

01成功率提高，但模型学会了反复重试

讨论中的假设业务例子：一个最多十轮交互的任务，只按最终是否成功评分。训练后成功率上升；这不是用户项目或 MiMo 的实测结论。

  1. 先观察成功率与平均奖励的上升，暂不把它解释为策略质量全面改善。
  2. 随机抽取完整轨迹，并专项检查工具调用量较高的成功样本，发现模型反复调用同一接口，靠多次尝试碰到成功结果。
  3. 对照逐轮反馈和最终奖励，确认评分只认可最终成功，未反映重复尝试的成本。
  4. 检查业务是否允许这种重试、是否有真实成本，并区分接口偶发故障与策略无效重复；据此决定是否调整评价或约束，再观察新轨迹和独立评测。

得到什么
成功率回答成功次数有没有增加，轨迹回答成功是怎样得到的。只有结合业务要求与评分机制，才能判断该行为是否值得强化；不能仅凭重试就判定作弊。

A MOMENT TO RECALL

训练成功率上涨，为什么还要随机抽查完整 rollout？MiMo 的通知能证明实时看板存在吗？

想一想，再展开答案

聚合指标可能遮住重复尝试、利用评价漏洞等行为，而这些轨迹还会影响后续更新；随机抽查能发现尚未触发指标告警的模式。MiMo 通知只证明训练期间检查过日志并据此干预，不足以确定监控频率、平台形态或具体不良模式。

工具过载：Intent Router、动态加载与生产兜底

工具多时应减少每次请求可见的候选，而非仅拆文件；常用预置、长尾按需，并以权限、校验、有限重试和评测约束动态选择。

01

理解概念

回到当时的问题

从“工具很多会不会撑爆”讨论上下文成本，再比较意图路由与模型自主找工具，并归纳面试中关于延迟和稳定性的回答。以下是设计方案，尚未在单工具 Demo 中实现。

过载在哪里：代码文件与模型上下文不同

当前 Demo 每次请求发送全部可用工具的名称、描述和参数格式，不发送执行函数源码。工具过多会占用上下文和输入 Token，相似说明增加选错工具的风险；不等于必然幻觉，也不能声称延迟一定按工具数线性增长。

按业务拆成 order-tools.mjs、product-tools.mjs 只改善维护；如果最终全部注册并发送，输入大小没有下降。真正控制上下文需要选择当前子集，同时给历史消息和输出留预算。

前置 Router 与模型自主加载的取舍

Intent Router 先按规则、分类器或模型判断业务，再提供相关工具。边界明确的高频场景容易控制和测试，但分错类会遗漏能力；使用模型路由时也要计入其请求成本与延迟。

Dynamic Tool Loading 可先只提供 search_tools 这样的 Meta-tool，让模型搜索能力，再由宿主把获准的工具定义加入后续请求的活动列表。仅返回名字不等于工具已变成可调用，加载和注册仍需系统实现。该机制灵活，但增加搜索轮次和检索失败点。

混合方式是常用工具预置，长尾能力按需检索。跨业务任务允许加载多组工具并动态补充，不把一次意图分类当作永久边界。筛选阶段关注所需工具有没有进入候选，后续选择阶段关注模型有没有用对工具。

响应速度：先减少往返，再优化每轮

查物流的高频请求可直接提供订单和物流工具，省掉模型先调用 search_tools 的往返。能从请求确定候选时由应用提前检索，一次加载必要的相关工具组，避免逐个发现；预置过多又会回到过载问题。

缓存工具定义和候选结果，并按版本、租户、权限范围失效。不能将工具元数据缓存等同于缓存实时订单状态。比较端到端 P95 延迟、Token 和任务成功率；减少一次搜索但导致更多纠错，并不一定更快。

生产稳定性：模型选择，系统约束

只允许检索经审核且当前用户有权使用的工具；明确相近工具的适用条件。检索失败时允许改写问题或扩大候选，但限制次数和预算；仍不确定就澄清、退回适用的固定流程或转人工。

执行前校验工具名、Schema、权限和业务条件；危险写操作按风险增加确认，重复请求用幂等机制防止重复效果。模型找到“创建发货单”不代表用户查询物流授权了写操作。

记录检索候选、选择、调用和结果，监控工具检索召回率、选用正确率、任务成功率和 P95。不能用参数格式合法证明业务选择正确，不能用一次成功示例证明生产稳定。

02

把概念放进示例

01200 个工具中处理“A1001 到哪了？”

假设系统有订单、商品、营销等 200 个工具，这是对当前订单 Demo 的扩展设计，不是实测规模。

  1. 前置路由判断为订单/物流问题，先只提供 lookup_order 与 lookup_delivery。
  2. 模型调用订单工具获取信息，再按需要调用物流工具，最后回答。
  3. 若用户接着问能否退款，系统允许补充退款资格查询工具，而不是由于初始分类就永久排除。
  4. 若路由不确定，可以澄清或通过 search_tools 检索；宿主验证权限并把选定 Schema 放入下一次请求。
text
全量目录：200 个工具（应用侧维护）
当前候选：lookup_order、lookup_delivery
请求 → 选择工具子集 → 模型调用 → 校验执行 → 回填结果
缺少能力 → 受限检索 → 更新活动工具集 → 继续

得到什么
减少每次发送的无关工具，同时保留跨业务补充能力。数量 200 仅为教学假设，没有测量性能收益。

02找错工具时不让错误升级为写操作

用户只问订单位置，检索却返回创建发货单工具。

  1. 候选层明确查询与创建的不同用途，并限制用户可用能力。
  2. 如果仍提出写操作，执行层检查用户授权及业务条件，不因模型选择而自动放行。
  3. 返回可纠正的错误，允许有限次重新检索物流查询；无法确定时询问用户。
  4. 记录失败阶段，加入回归任务集，检查错误工具被检索到或被错误选择的原因。

得到什么
预期通过多层约束减少误操作并恢复任务；这是方案分析，尚未在 Demo 中实现。

A MOMENT TO RECALL

工具拆成多个文件能解决过载吗？Router 和 Meta-tool 应如何选择？

想一想，再展开答案

拆文件只改善组织，需减少每次发送的 Schema 子集才控制上下文。高频明确任务优先直接路由，长尾开放任务按需搜索；混合使用，允许跨业务补充，并由执行层约束权限和业务条件。
